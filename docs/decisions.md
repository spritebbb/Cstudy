## 2026-10-10 项目立项

### 目录名从 `D:\Cstudy！` 改成 `D:\Cstudy`

**原因**：原目录名结尾是全角「！」。FFmpeg、gcc 这类命令行工具在处理非 ASCII / 全角路径时
会出各种难定位的编码错误。趁项目还没有文件时改掉，成本最低。

### Python 用 3.12，不用机器上已有的 3.14

**原因**：机器上只有 Python 3.14。`faster-whisper` 依赖的 `ctranslate2`、以及 PyTorch，
在 3.14 上轮子可能还没发布，装到一半失败会非常难排查。单独装一个 3.12 并建独立虚拟环境，
不动用户现有的 3.14 和 LibreOffice 自带的 Python。

### AI 服务用 DeepSeek，模型用 `deepseek-flash`

**原因**：用户原本以为自己的 Claude Code 接的是 DeepSeek，实际查 `~/.claude/settings.json`
发现接的是**阶跃星辰 StepFun**（`api.stepfun.com/step_plan`，模型 `step-5-preview`）。
两者是不同的服务，Key 不通用。用户选择自行申请 DeepSeek Key。

**模型名**：用户原提示词里写的 `deepseek-v4-flash` 和 `deepseek-v4-flash-vision-exp`
**已经退役**（官方文档说明这两个名字仍兼容但会转到 V4.1-Flash）。
实测 `GET https://api.deepseek.com/models` 当前只有两个模型：

- `deepseek-flash` —— 100 万上下文，`input_modalities: ["text","image"]`，**支持图片输入**
- `deepseek-v4-pro` —— 100 万上下文，纯文本

**关键决策**：用 `deepseek-flash` **一个模型同时处理文字和图片**。
原方案要配两个模型（文本一个、视觉一个），现在配置项和出错点都少一半。

### 语音转写用本地 faster-whisper

**原因**：用户机器有 RTX 4060 Ti 8GB，本地转写免费且离线。
代价是 PyTorch + CUDA 体积大、安装慢，且必须配 Python 3.12。

**保留 CPU 回退**：`transcribe.device: auto` 会优先尝试 CUDA，失败自动退回 CPU（int8）。
用户不会 Python，不能因为 CUDA 环境没配好就整个功能不可用。

### B 站字幕走扫码登录

**原因**：B 站字幕接口需要登录态。写一个扫码登录窗口，登录一次把 cookies 缓存到
`data/cookies/bilibili.json`（已 gitignore），之后不用重复登录。

### 笔记导出到项目内 `notes/` 文件夹

**原因**：用户暂时不需要 Obsidian 集成。同时写两份：数据库一份（供出题和复习用），
文件一份（用户能直接打开看）。导出目录做成配置项，以后想接 Obsidian 只改 `config.yaml`。

### 第一版范围：只做端到端主链路

**原因**：遵循"先做最小闭环"。第一版只做 导入链接 → 抓字幕 → 生成笔记 → 出题 → 入库 + 一个能点的窗口。
错题本、刷题界面、抽帧看图全部推迟。

## 2026-10-10 首次真跑后的一轮修正

第一次拿真视频跑通整条链路，暴露了下面这些问题。记录在这里，免得以后又走回去。

### 字幕轨要挑覆盖最全的那条，不能挑第一条

**原因**：B 站一个视频可能同时挂人工字幕和 AI 字幕，而**人工字幕有时只覆盖开头一小段**。
实测 `BV17a7K64ELH` 第 7 P（时长 897 秒）：

| 轨 | 条数 | 覆盖 | 字数 |
|---|---|---|---|
| `zh`（人工） | 10 | 45 秒 | 161 |
| `ai-zh`（AI） | 501 | 895 秒 | 4805 |

取"第一条中文轨"会拿到 45 秒的开场广告，把整节 15 分钟的课全丢掉。
语言判断要用 `"zh" in lan` 而不是 `startswith("zh")`——AI 轨的 lan 是 `ai-zh`。

**另外**：覆盖不到视频 30% 时判定不可用，退回语音转写。宁可慢一点，也别拿广告出题。

### 提示词必须明确"只整理 C 语言技术内容"

**原因**：就算字幕里有真内容，笔记也会把开场白、互动引导、学习鸡汤一起收进去，
出题再照着笔记出。判断标准写成一句话：**"这条内容能出现在专升本 C 语言试卷上吗？"**

**禁止重复题**：实测发现同一节课出了五对重复题（两道题都在问"C 语言之父是谁"）。
出题和复查两处都明确写了"同一知识点只考一次"，光靠模型自觉不行。

### 允许出 0 道题

**原因**：原来 `parse_questions` 把"0 道题"当错误抛异常，逼着模型凑数。
**"这节没有可考内容"是正确结果**，硬凑出广告题才是错的。开场课、导学课就该 0 道。

### 生成完让 AI 再复查一遍（二次校准）

**原因**：用户不会 C 语言，判不了对错，也不该负担逐题核对——他是唯一的把关人这件事本身就是设计缺陷。

**做法**：笔记和题目生成完，各再调一次 AI 复查。能修的自动修（答案错、题干歧义），
改不动的删掉（广告题、编造题），并把"删了哪几道、为什么"显示在界面上。

**笔记复查必须带原始字幕**：不带就只能校对文字，查不出"笔记编造了字幕里没有的内容"，
而编造恰恰是最危险的一种错。

**复查失败不是致命错误**：原来的内容照常保留，只是这一轮没人把关而已。
所以 `Reviewer` 一律不抛异常，用 `ReviewReport(ok=False, error=…)` 表达。

### 题目数量改成动态

**原因**：原来写死 7 道（选3+填2+阅1+编1），一节 5 分钟的概念课和一节 30 分钟的指针课
拿到的题量一样，跟内容多少完全脱钩。

**做法**：`quiz.count: auto` 让 AI 按内容多少决定，代码强制 `min_count~max_count` 范围兜底。
超上限截断，低于下限**不补题**（少几道练着比硬凑废题强）。
想固定数量就把 `count` 填成数字。

## 2026-10-10 刷题界面

### "开始刷题"按钮以前是个谎

它其实只是出题，把题目渲染成 Markdown 塞进只读控件——用户看得到题，没法作答。
现在换成真正的答题面板（`ui/quiz_panel.py`），"题目" tab 改名"答题"。

### 只有选择题自动判分，其余自己对照

**原因**：`Question.answer` 是 AI 原样返回的自由文本。填空题答案是 `"48"`、`"65~90"`
这类，阅读题是程序输出，编程题是参考代码——**后三种没法可靠地自动判分**。
硬判只会误伤：答案写法稍有不同就判错，用户会以为自己答错了，比不判分更糟。

**判分逻辑单独放 `cstudy/grading.py`，不 import Qt**：判分是最容易出错的部分，
跟界面解耦才测得好（现在有 24 个单测）。界面只做搬运。

**规范化必须扛得住 AI 不守规矩**：实测见过 `"B"` / `"b"` / `"Ｂ"`（全角）/
`"B. 选项内容"` / `"答案：B"` / `"选 B"`。直接字符串比会把这些全判错。
**规范不出来时返回 None，不猜**——老实说"这题没法自动判，你自己对照"。

**用户选的是下标，比的是字母**：AI 给的选项顺序可能漂移（同一题重出一次
B 和 C 调个个儿），比下标就错了。

### 答对了不删错题记录

`wrong_questions` 表里有 `mastered` 和 `next_review_at`，明显是为遗忘曲线留的。
**什么时候算"掌握"、隔多久复习，该由专门的错题本功能来定**，不该在刷题界面
顺手发明一套"答对就删"的规则——删了就丢了"我以前错过这道题"这个信息，
而错题本的价值恰恰在这里。所以这里只做累积：答错记一笔，答对什么也不做。

### 顺手补上 questions.point 列

`questions` 表原来只有恒为 NULL 的 `point_id`，没有 `point`（AI 给的知识点文字标签），
所以从题库加载出来的题会丢掉"知识点"。补了这一列，并在 `init_schema()` 里
用 `ALTER TABLE` 给老库做迁移——`CREATE TABLE IF NOT EXISTS` 不会改已存在的表。

## 2026-10-10 导入现成题库

### 先做"粘贴文本"，不做文件解析

用户想找湖北专升本的 C 语言题库，但搜不到（见下）。做导入功能前问了他手上有什么，
答案是"还没找到，先支持粘贴"。

**粘贴文本这条路最通用**：从网页、PDF 阅读器、Word、聊天记录里复制出来都能用，
而且**不需要新装任何库**。等真有 PDF/Word 文件了再加文件读取也不迟
（PDF 要 pypdf，扫描件还得 OCR，那是另一个量级）。

**湖北专升本的题库这件事**：湖北专升本的专业课是**各招生院校自主命题**，
不存在全省统一的题库——用户要找的其实是某所具体院校的真题。这一点记在
用户画像里了，以后聊到题库先问清目标院校。

### 按题号切块，不按字符硬切

粘贴的文字可能很长，要切成几段分别送给 AI（一次返回太长会被截断）。
**按字符切会把一道题劈成两半**，AI 拿到半道题只能丢掉，用户少了几道还不知道。
所以按题号（`1.` / `1、` / `1)` / `第1题`）切，每块都从题目开头开始。
第一个题号之前的"一、选择题"这类说明文字也要留着。

### 导入的题不做 AI 复查

其他地方的题目生成完都会过一遍 AI 复查，**导入这条路刻意不做**：
原文（尤其是真题）是权威的，让 AI 去"纠正"答案反而可能把对的改错。

改成**入库前先给用户看一遍预览**，确认了才保存——人来把关比 AI 把关更靠谱。

### 导入时按题干去重

同一份材料导两次会把题目翻倍。保存前拿题干跟库里已有的比一遍（忽略空白差异），
重复的直接跳过并告诉用户跳了几道。

## 2026-10-10 按目标院校对齐考纲

### 考纲换成汉江师范学院的（四所候选里范围最大的）

用户考的是**湖北专升本**，专业课由**各招生院校自主命题**，没有全省统一题库。
筛出四所"专业课只考 C 语言一门"的学校后（湖北工程学院、武汉商学院、
汉江师范学院、湖北师范大学），用户要求"按能最大程度覆盖的来"。

**汉江师范学院的考纲范围最大**——包含其余三所的全部内容，另多出"预处理命令"。
按它复习，四所都覆盖。考纲全文在 `syllabus.yaml` 里，来源和依据写在文件头。

### 出题关掉选择题

**四所目标学校都写明"无选择题、无判断题"**（湖北专升本的英语统考也是）。
工具原来默认出 3 道选择题，对这四所全是白刷。

改动有两处，**缺一不可**：
- `config.yaml` 的 `quiz.prefer.choice: 0`
- `quiz_user_prompt()` 里加"**本次只出这些题型**：…，不要出其他题型"

只改第一处不够——`prefer` 原来只是"比例参考"，AI 会顺手补几道选择题。
现在填 0 的题型是**限定**，不是参考。

### 出题比例按题型分值折算

湖北工程学院是四所里唯一公布题型分值的（填空 48 / 程序阅读 35 /
程序填空 36 / 程序设计 31，共 150 分），按它折算成题量比例：
填空 5 : 程序阅读 2 : 程序设计 2。

### 换考纲要清库

`scripts/seed_syllabus.py` 是按知识点名字 upsert 的，**旧考纲的条目不会自动删**。
换考纲后要先 `DELETE FROM syllabus_points` 再灌，否则新旧混在一起。
（旧的 109 条已清掉，现在是 10 章 64 条。）

### 导入题库也过滤选择题

出题关掉选择题还不够——**导入现成题库时也要过滤**。市面上的题库几乎都带选择题，
不过滤的话会混进来一堆考不到的，白刷。默认过滤 `choice`，配置项在
`config.yaml` 的 `import.skip_types`。

**关键设计：先让 AI 全部解析出来，再在代码里过滤。** 不是让 AI 直接跳过选择题——
那样万一它顺手把别的题型也跳了，就悄悄丢题了，而用户根本发现不了。
改成"代码过滤"之后，`ImportOutcome` 会把**解析出几道 / 有几段没解析成功 /
过滤几道 / 去重几道 / 最终保留几道**五个数字全摆在界面上，用户能一眼核对有没有少题。

**"有几段没解析成功"必须报出来**：网络抖动会让某一段整体失败，那一段的题一道都进不来。
这是最容易悄悄少题的一条路，如果不说，用户看到"保留 N 道"会以为全都解析到了。

**先过滤再去重**：顺序反了会把"重复的选择题"也算进去重数里，两个数字就都不准了。

整份材料全是选择题时**报错而不是静默返回 0 道**，并说清是哪种题型被滤掉了几道——
静默返回 0 道用户会以为工具坏了。

**`skip_types` 写错要报人话**：用户手改 `config.yaml` 时很可能漏掉前面的 `-`，
写成 `skip_types: choice`。字符串被直接遍历会**逐字符**拆成 `{'c','e','h',...}`，
跟任何题型都不匹配，过滤静默失效（用户还以为工具坏了）。所以裸字符串按"就这一项"处理，
写成数字之类则抛 `ConfigError` 说清楚该怎么改，而不是让 `'int' object is not iterable` 冒到界面上。

**预览标题用"最终保留"**：状态栏的"解析出"是过滤**前**的总数，预览标题原来也写"解析出 N 道题"
却是过滤**后**的数——同一个词指两个数，用户核对时反而更懵。

## 2026-10-10 批量导入题库文件

### 文件导入走脚本，不塞进界面

上面"先做粘贴文本，不做文件解析"那条决定**被现实推翻了**：用户从闲鱼买到了题库，
**127 个文件、119MB**，粘贴这条路走不通（文件太多，用户也不会 Python）。

所以加 `scripts/import_bank.py`，**刻意不塞进界面**：
- 界面上的导入是"粘一段文字"的交互形状，选文件夹、批量、断点续传都不是它的样子
- 这类一次性批量操作脚本够用，做进界面反而要多维护一套文件选择 UI

### 抽文字：pypdfium2 比 pypdf 好很多

同一份 PDF，**pypdf 会把每个词甚至每个字符拆成一行**（"专升本\nC\n语言\n试卷一"），
AI 得多花力气去拼；**pypdfium2 抽出来是正常成行的**。两者字数差不多，
差别全在可读性上——所以优先 pypdfium2，读不了（少数加密 PDF）再退回 pypdf。

其余格式：
- `.docx` → 标准库 `zipfile` 直接读 `word/document.xml`，**不装 python-docx**
- `.doc`（老式二进制）→ LibreOffice 命令行转换（`soffice --headless --convert-to txt`），
  转换时给一个独立的 `-env:UserInstallation`，免得跟用户开着的 LibreOffice 抢
- `.xls` / `.pptx` → **不支持**。判断题不是目标题型，PPT 是讲义不是题

### 扫描件直接跳过，但要报出来

抽出来不到 200 字的基本是扫描版 PDF（`慧航/`、`机构卷子2025/`、小绿书都是），
要 OCR 才行——那是另一个量级的事。**明确列出来**，不静默跳过，用户才知道少了什么。

### 默认不重复导

按 `questions.source` 记已经导过的文件，重跑不会翻倍。跨文件也会跟库里已有的题干
比一遍——不同学校的卷子重复度很高（`慧航/` 和 `机构卷子2025/` 就是同一批文件）。

### 过滤和报数原样复用

`QuestionImporter` 直接复用，所以选择题照样被 `skip_types` 滤掉，
"解析出几道 / 几段没解析成功 / 过滤几道 / 去重几道 / 入库几道"照样全报。

### 题目和答案必须待在一起，否则 AI 只能瞎猜答案

全库导完一查：**1156 道题里 526 道（45%）的答案是 AI 推断的**。对备考来说这是
硬伤——AI 猜错一个数字，用户就背错了。

查下来是两个原因，**都不是"原文没有答案"**：

1. **切块把答案切走了**。一份 8473 字的卷子，答案区从第 7895 字开始，
   而切块边界在 7976——第 1 块有题目没答案、第 2 块有答案没题目。
   按题号切块的逻辑本身没错，错在**没意识到文末还有一大块"参考答案"**。
2. **题目和答案分成两个文件**。题库常见排版：`模拟试卷11.doc` +
   `模拟试卷11参考答案.doc`；`c语言模拟题15套.pdf` + `c语言试卷15套参考答案.pdf`。

**修法**：`split_answers()` 把文末答案区切出来，作为 `reference` **附给每一段**
（不是只给最后一段——题目是分散在各段里的）。外部的答案文件也走同一个
`reference` 参数。提示词里明确要求"优先从参考答案里找，按试卷标题和题号对应"。

**踩的坑**：正则 `[ \t]*$` 匹配不上答案标题，因为 PDF 抽出来的文字是 `\r\n` 换行，
`$` 前面还杵着一个 `\r`。行尾必须写成 `[ \t\r]*$`。（`.bat` 换行也踩过同类坑。）

**配对只认文件名，认不出就不配**：一度想"文件夹里只有两个文件就配一对"，
但 `谭浩强课后答案.pdf` 和 `小绿书.pdf` 正好同处一个文件夹，会把答案配错。
**配错的答案看着像真的，比标着"AI 推断"的更坑**。拿不准的用 `--answer-key` 手动指定。

效果：`专升本C语言 试卷附答案六.pdf` 重导后 18/18 全部来自配套答案，逐题核对无误
（AI 还顺手修了两处 OCR 错字：`ch,=` → `ch<=`、`x=0` → `x==0`）。

### 提示词要分清"程序填空"和"程序设计"

第一次真导（`c语言试卷湖北/` 那 9 个文件）就发现：11 道 `coding` 里有 3 道其实是
**程序填空**——题干代码里留了空（`max= ;`、`t=t n`），答案是 `printf; scanf; b; <; max`
这种填空值，不是完整程序。

根因是 `IMPORT_SYSTEM` 只列了 type 有哪四种，**没说这两种怎么分**。
AI 看到题干里有代码就判成 `coding`。

**必须修**：湖北工程学院的卷子里程序填空占 36 分，跟程序设计是两道不同的大题，
全标成 `coding` 会让题型分布整个偏掉，后面按题型统计考纲覆盖度也就没意义了。

修法是加一条规则，判据**写死成"要不要你写整段程序"**，而不是"题干里有没有代码"——
因为程序填空的题干里照样有代码，这是 AI 判错的根源。修完把那个文件重导验证：
3 道全部正确落到 `fill`，题干还自动补上了"请填写程序中各空缺处的内容"和 `______` 空格标记。

## 2026-10-10 刷题筛选 / 考纲覆盖度 / 真题组卷

题库从 6 道涨到一千多道之后，界面就不够用了：点「开始刷题」把全部题塞进一个队列，
没法只刷指针、只刷编程题、只刷某一份卷子。

### 挑题做成对话框，不做成常驻的筛选栏

点「从题库挑题」弹一个对话框，选完再加载。默认全选，**直接回车就是"全刷"**，
不想筛的人不多点一下。做成常驻筛选栏的话，答题页面会被挤掉一块，
而绝大多数时候用户只是想在某个范围内刷几道。

### `point_id` 这一列早就建好了，只是没人写

`schema.sql` 里 `questions.point_id` 带着外键指向 `syllabus_points(id)`，
还建了索引，注释写着"暂时没用上，恒为 NULL"。这次把它用起来：
`Question` 加字段、`save_questions` 写它、`assign_points` 按标签批量对齐。

**对齐只认标签，不认题目内容**：让 AI 把 805 个不同的自由文本标签
（"递归函数""带参宏定义"）映射到考纲的 64 个知识点，比逐题重新判定便宜得多。
**对不上的一律留空**——硬塞会让覆盖度变成假数据，用户以为某个知识点练过了，
其实没有。提示词里专门写了"题型名不是知识点"（"程序设计""程序填空"这类）。

### 覆盖度统计必须用 LEFT JOIN

没题的知识点**也要出现在结果里**（0 道）。用 `LEFT JOIN` 而不是 `JOIN` 就是为了这个：
用户要看的是"哪些知识点还没练到"，漏掉 0 的那些，这个功能就没有意义了。
界面上 0 道的用红字标出来。

### 组卷不需要 AI

「组一套真题」是从**已有的题**里按分值比例随机抽，跟 `ai/quiz.py` 那条
"从笔记生成新题"完全是两回事——那条要调模型，这条只是筛选，不花钱。
所以模块放在 `src/cstudy/exam.py` 而不是 `ai/` 下面。

**题型口径的坑**：考试是四类（填空/程序填空/程序阅读/程序设计），
而库里的 `type` 只有三类——`fill` 把"填空"和"程序填空"合并了（48+36=84）。
配置里 `exam.ratios` 按 84:35:31 写，并在注释里写清楚这个合并。
以后要分开统计，得先给 `questions` 加个题型字段。

**题量用最大余额法分配**：逐个四舍五入会让总数对不上（要 20 道算出 19 道）。
先按比例取整，余数给小数部分最大的那几个题型。

**某题型不够时如实少给**，不拿别的题型凑数，并在界面上说明差几道。

### 答案区标题允许带"第N部分"前缀

`split_answers()` 原来只认整行就是"参考答案"的标题。小绿书用的是
**"第2部分  参考答案"**，于是整本书 245101 字的正文里，那 42730 字的答案区
没被识别出来，答案只能靠 AI 猜。正则放宽成允许"第N部分/第N篇"前缀。

## 2026-10-10 错题本与遗忘曲线

### 数据层早就现成，缺的只是界面

`wrong_questions` 表一直就在：`record_answer()` 每次答错都往里写错次数和最近错的时刻，
`schema.sql` 里甚至已经建好了 `next_review_at`（注释写着"遗忘曲线下次复习时间"）
和对应的索引。**但整个界面没有任何地方读它**——数据在记，没人看。
`record_answer()` 的注释也写明了："什么时候算'掌握'、隔多久复习，留给专门的错题本功能去定。"

所以这一版只补了读的那一半，`record_answer()` 一行没动。

### "掌握"是算出来的，不写库

一道题**连续答对 N 次**（默认 2 次）就算掌握。这个状态由 `answers` 表的历史实时算出来，
不往 `wrong_questions.mastered` 里写。

这样不会出现"字段说掌握了、实际答题记录不是"的不一致——那种不一致一旦出现，
用户就没法信任错题本了。`mastered` 那一列只留给用户**手动**点"这个我会了"。

**注意是"连续"**：中间错一次，计数从头开始。以前对过两次不代表现在还熟。

### 时区：SQLite 的 CURRENT_TIMESTAMP 是 UTC

`last_wrong_at` 由 SQLite 的 `CURRENT_TIMESTAMP` 写入，**那是 UTC**，
而 `datetime.now()` 是本地时间。直接比会让「该复习了」差好几个小时
（东八区差 8 小时，对"隔 1 天复习"来说是三分之一的误差），
显示的"最近错于"也会跟用户表对不上。

所以 `_parse_time()` 读出来时统一 `astimezone()` 转成本地时间再往外传。
**这个坑在别的表上同样存在**（`answers.answered_at`、`notes.created_at`），
以后要显示它们的时间也得走这一步。

### 复习间隔按错次数递增

错第 1 次隔 1 天、第 2 次 3 天、第 3 次 7 天、第 4 次起 15 天。
错得越多说明越不熟，但也不该天天刷同一道——间隔拉开才叫遗忘曲线。
间隔写在 `config.yaml` 的 `wrong_book.review_intervals`，写错了退回默认值。

## 2026-10-10 关键帧读屏（做出来了，但默认关着）

### 为什么做

笔记原来只从字幕生成，**老师屏幕上写的代码和 PPT 全丢了**——字幕说"我们写一个 for
循环"，真正的代码在屏幕上。这是产品最初设想里的一块。

技术上跑通了：yt-dlp 下 480p 低清视频（实测两分钟才 1MB）→ ffmpeg 按**画面变化**
抽帧（`select='gt(scene,0.3)'`，两分钟只抽 7 张）→ 发给 `deepseek-flash` 读屏。
实测 AI 能把 VS 编辑器里的完整代码、PPT 目录和正文、控制台输出一字不差读出来。

### 为什么默认开着（2026-10-11 更正）

**这条我判断错过一次，记下来别再犯。**

一开始我把 `frames.enabled` 设成 `false`，理由是：用户主要靠导入的题库刷题，
每集多下一次视频 + 几次 AI 调用不划算。**这个理由是建立在一个错误假设上的。**

用户纠正了我：他的实际用法就是 **看视频 → 生成笔记 → 根据视频出题 → 刷**。
视频链路是主链路，不是次要路径。

顺着这条线查到一件更要紧的事：**CC 字幕里一个代码符号都没有**。实测那个 27 分钟的
for 循环课，字幕 9754 字全是口语，`#include`、`printf`、`for(`、`{`、`}` 出现次数
**全是 0**。而生成的笔记里有完整规范的 C 程序——**那是 AI 自己补写的，不是老师
屏幕上写的**。对拿它备考的人来说，这个差别很要命：变量名、例子、细节都可能跟课上不同。

**关键帧正是补这个洞的**：让代码来自屏幕，而不是 AI 补。所以默认改成 `true`。

教训：**不要用"用户大概怎么用"去替他决定功能值不值得做**。这次是直接问了才知道自己
假设错了。代价是每集多下一次低清视频（480p 约十几 MB）+ 几次看图调用——真实但不大。

### 两个实现上的坑

- **帧必须带时间戳**。字幕是有时间戳的（`[MM:SS]`），屏幕内容也带上时间，

## 2026-10-11 给题量不足的知识点补题

### 覆盖度查出来的问题

对齐考纲之后一看，**考试的重头反而题最少**：指针的概念只有 3 道、用指针处理变量
3 道、文件定位 2 道、内部函数与外部函数 1 道，还有 7 个知识点一道没有。
题库一千多道，但分布是偏的——真题卷子爱考什么，市面题库就堆什么，
冷门知识点没人出题。

所以加了 `scripts/fill_gaps.py`：把题数少于 5 道的知识点列出来，一个个出题。
实测 16 个知识点补了 **90 道**。

### 跟"从笔记出题"不是一条路

`ai/quiz.py` 那条是从**课程笔记**出题，有原文可依；补题**没有笔记，只有知识点本身**，
所以提示词（`GAP_SYSTEM`）得要求按"这个知识点真题一般怎么考"来出，并且
**答案必须唯一确定**——不能出"以下说法正确的是"这种没有唯一答案的题。

出完照样过 `Reviewer` 复查。复查的"依据"用知识点本身拼一段话传进去，
不然复查没有判断答案对错的根据。

### 我判断错了一次

我一开始跟用户说："那几个空的理论知识点（用流程图/N-S 图/伪代码表示算法）
本来就不该有题，试卷上不会让你做题。"

**这是想当然。** AI 对着这些知识点出的题很正经：

- 「用流程图表示算法时，表示算法的开始和结束应使用 `______` 框」→ 起止框
- 「用 N-S 流程图表示算法时……」
- 「C语言最初是由美国 `______` 实验室的 Dennis Ritchie 于 1972 年设计完成的」→ 贝尔

都是考纲内的填空题。**"我觉得不会考"和"考纲里写着"是两回事**——
考纲既然列了，就该有题练。以后不要用自己的判断替用户决定"这个不用练"。

### 每道题都必须有答案

用户明确要求过。四道关，缺一不可：

1. 提示词里要求答案唯一确定
2. `Question.__post_init__` 拒绝空答案（`DataError`）
3. `parse_questions` 会跳过不合格的题
4. 入库前 `GapFiller` 再过滤一次，脚本最后查全库报"没答案的 0 道"

## 2026-10-11 把"程序填空"和"程序阅读"从"填空"里分出来

### 起因：用户问"考纲做到完全覆盖专升本题型了吗"

一查，**没有**。考试是**四类**题型，库里只有**三类**：

| 考试题型 | 分值 | 库里的 `type` |
|---|---|---|
| 填空题 | 48 | `fill` |
| 程序填空题 | 36 | `fill` ← 和上面合并了 |
| 程序阅读题 | 35 | `reading`（但有一批被标成了 `fill`） |
| 程序设计题 | 31 | `coding` |

**程序填空占 36 分，比程序阅读（35）和程序设计（31）都高**，却跟普通填空混在一起，
既筛不出来、也不能按考试结构组卷。这是硬伤，不是瑕疵。

### 顺带查出一个更早的数据问题

一开始我按"题干带代码 + 有空白"判程序填空，结果判出来 654 道，一看样例**全是**：

> 以下程序运行后的输出结果是 ______ 。 main() { int x=2006,y=2007; printf(...); }

这是**程序阅读题**——当初因为题干里有个 `____`，被 AI 标成了 `fill`。
也就是说库里一直有一批程序阅读题藏在"填空"里，而且没人发现。

### 判据：看"空在哪儿"

区分这三者，关键不是"有没有代码"，而是**空在哪儿**：

- **普通填空**：没有代码，或代码只是背景，空在问句里 → `fill`
- **程序填空**：空**在代码里面**，而且是好几个（`______(...)`、`max= ;`）→ `code_fill`
- **程序阅读**：给一段程序，空在问句里（"输出结果是___"）→ `reading`

具体两条，都是踩出来的：

1. **空括号 `()` 不能当空算**。一开始把 `\(\s*\)` 当成"要填的地方"，结果
   `main()`、`printf()` 全被当成空——**这是第一版误判 654 道的根因**。
   只认下划线、【】、全角括号。
2. **光看有没有 `{` 不够**。`int a[3]={1,2,3}; 则 a[0] 的值为___` 里的花括号
   只是数组初始化，不是"一段程序"。判程序阅读要求**像一段程序**
   （有函数定义或 `#include`）。

判据做成 `models.exam_type_for(qtype, question)`，`Question.exam_type` 和
数据库回填共用同一个函数——避免两处逻辑各改各的。

### "考试题型"是一列算出来的数据，不是新类型

没有往 `VALID_TYPES` 里加类型，而是加了 `questions.exam_type` 列，
由 `exam_type_for()` 算出来、入库时写进去。好处是：

- **老的 1848 道题不用重新导、不用调 AI**，启动时 `backfill_exam_types()` 自动补
- 提示词不用改（改了又要重跑一遍导入）
- 判据是确定的、能解释的，不像 AI 标注那样说不清为什么

用 `exam_type` 筛选和组卷，`type` 保持原样不动。

### 结果

| 考试题型 | 题数 |
|---|---|
| 填空题 | 881 |
| 程序阅读题 | 485 |
| 程序设计题 | 417 |
| **程序填空题** | **65** |

组一套 20 道的卷子现在出来的是 **填空 6 / 程序填空 5 / 程序阅读 5 / 程序设计 4**，
跟 48:36:35:31 对得上（以前只能给 84:35:31）。

**程序填空只有 65 道，是偏薄的**——它占考试的 24%，题库里 65 道能组 13 套卷子，
够用但不宽裕。以后可以像补题那样对着它补一批。

## 2026-10-11 题干不能当 Markdown 渲染

用户截图反馈"这些排版太难看了"，两个症状：

1. **`#include <stdio.h>` 变成了超大的标题**——因为 `#` 是 Markdown 的标题符号
2. **整段代码挤成一长条**——因为 Markdown 里**单个换行等于空格**，
   代码的每一行被拼成了一句话

根因是 `question_view.setMarkdown(question.question)`：题干是**代码**，不是 Markdown。
参考答案和解析（`feedback_view`）也是同一个毛病，"导入题库"的预览同理。

**修法**：`ui/rendering.py` 的 `material_html()`——先 `escape()` 转义，
再放进 `<pre style="white-space:pre-wrap">`。`<pre>` 保住换行和空格、自带等宽字体
（代码看着对得齐），`pre-wrap` 让太长的行照样折行，转义保证 `<stdio.h>`、`&&`
这些不会被当成 HTML 标签。

三处都用它：答题页的题干、参考答案和解析、导入预览。

**教训**：**用户给的内容不是 Markdown，别拿 Markdown 渲染器去显示它。**
`setMarkdown` 看着方便，但它会重新解释文本——而代码里满是 `#`、`*`、缩进、
单个换行，全都是 Markdown 的语法。凡是显示"原材料"（题干、答案、代码、
用户粘贴的文字），一律用 `<pre>` 或纯文本。

**验证方式**：这个项目的界面没法真的点，但可以**离屏渲染成 PNG 看一眼**——
排版问题光看代码判断不了。写了 `scripts/_render_preview.py` 临时脚本
（`QuizPanel.grab().save(...)`）渲染出来确认过了。

## 2026-10-11 界面字体：换掉那套又小又虚的默认字体

用户反馈"字体不好看、太伤眼"。查下来**根因是没设字体**：

`<pre>` 不指定 `font-family` 时，Qt 落到纯 `monospace`——在 Windows 上就是
**Courier New**，细、发虚、字号还小。用 `QTextDocument` 验证过：裸 `<pre>` 解析出来
是 `['monospace']`、字号 `0`（用默认那套小的）。

**改法**：字体写进 `config.yaml` 的 `ui:` 段，启动时由 `run.py` 应用：

- 界面文字：**微软雅黑** 11pt
- 题干和代码：**Consolas** 12pt，中文兜底到微软雅黑

这台机器上验证过可用的字体（`C:\Windows\Fonts` 里确实有）：
微软雅黑 `msyh.ttc`、等线 `Deng.ttf`、Noto Sans SC `NotoSansSC-VF.ttf`、
Consolas `consola.ttf`。

**踩的坑**：`style` 属性里字体名带单引号，属性本身就必须用双引号——
写成 `style='...font-family:'Consolas'...'` 是**单引号套单引号**，
属性当场被截断，整套样式全失效。

**验证方式**：光看 HTML 字符串不算数，用 `QTextDocument.setHtml()` 之后
读 `charFormat().fontFamilies()` 和 `fontPointSize()`，确认 Qt **真的解析到了**
配置的字体和字号。

**顺带说明**：用户提到的 "Anthropic Sans" 并不存在——Anthropic 的品牌字体是
Styrene 和 Tiempos，都是授权字体，不会随系统装上，也没法塞进这个程序。
如实说明后换成了系统上确实有的好字体。

## 2026-10-11 下载慢？其实是"看不见进度"

用户问："这个下载低清视频为什么这么慢，真的有在下吗？"

**查下来的结论是：不是慢，是看不见。**

那段下载确实花了 4 分 32 秒下完 10.82 MB（约 41 KB/s），日志里清清楚楚。
可我随后用同样的命令、同一份文件重下了两次：

| | 耗时 | 速度 |
|---|---|---|
| 匿名 | 1 秒 | 7.2 MB/s |
| 带登录态 | <1 秒 | 20.9 MB/s |
| **用户那次** | **4 分 32 秒** | **0.04 MB/s** |

同一份文件差了上百倍——**B 站给的 CDN 节点时快时慢，跟登录与否基本无关**
（短片段实测带 cookie 只快 15%）。所以这不是能"修好"的毛病，是运气。

**真正该修的是"看不见"。** 界面上 4 分钟一动不动，用户当然以为卡死了。
所以 `_run_download` 改成 `Popen` 逐行读 yt-dlp 的输出，解析
`[download]  45.3% of ...` 报给界面，每涨 5% 报一次。现在能看到
`0% → 9% → 18% → 37% → 74% → 100%`。

顺带加的三样：

- **`--cookies`**：把登录态转成 yt-dlp 的 Netscape cookie 文件（字段 7 个、
  名字大小写必须对：`SESSDATA` 而不是 `sessdata`）。下载路径原本完全没带登录态。
- **`--concurrent-fragments 4`**：B 站的视频分片传，多开连接并排下。
- **`--retries 10 --fragment-retries 10`**：节点抽风时自己重试。

**教训**：用户说"为什么这么慢"，第一反应别去优化速度——先问"他看不看得见"。
一个要跑几分钟的操作，没有进度显示，体感就是卡死。

## 2026-10-11 编程题的「跑一下」：让编译器来教

### 这条我判断错过一次

之前我把"编程题 gcc 编译验证"判成**不值得做**，理由是"题库里不少编程题的答案
其实是代码片段，本来就编译不了"。

**那是在回答一个错的问题。** 用户要的不是"验证题库里的答案"，
是**验证他自己写的代码**——这 31 分光"写完对照参考答案"练不出来。C 语言恰恰是
**看着对、编译就报错**的科目（漏分号、少 `&`、数组越界），不跑一遍根本不知道自己会不会。

教训：判断"某个功能值不值得做"之前，先确认**它要解决的是谁的什么问题**。
我当时想当然地把"验证答案"当成了目标。

### 实现上的四个点

1. **编译和运行放后台线程**（`RunCodeWorker`）。代码里写个 `while(1)`，
   编译加超时要好几秒——主线程跑的话整个界面卡死。
   运行超时 10 秒，编译超时 60 秒。
2. **报错翻译成中文**（`runner.ERROR_HINTS`）。gcc 的报错是英文的，初学者看不懂。
   这里给的不是翻译而是**怎么办**：漏分号会说"多半是上一行末尾漏了分号，
   gcc 报的行号常常比真正出错的行晚一行"。
   用**正则**匹配不用字面串——第一次写死 `expected ';'` 就匹配不上，
   因为 gcc 报的是 `expected ',' or ';'`。
3. **只解释 error，不解释连带的 warning**。漏个分号会顺带报"变量没用上"，
   两条都解释反而把真正的原因淹了。
4. **认得出微软那套 `_s` 函数**：用户的课用 Visual Studio，老师的代码里很可能有
   `scanf_s`。不过**实测 MinGW 的 UCRT 版本自带它**，能编过——所以这条提示只在
   真的编不过时才出现。

### 编译器怎么装的

`winget install BrechtSanders.WinLibs.POSIX.UCRT`（MinGW-w64 / gcc 16）。

**踩的坑**：第一次装了十几分钟只下了 18 MB（GitHub 在国内的速度），
用户挂上 VPN 之后一分钟就下完了。所以装编译器这种事，**先提醒用户开代理**。

`find_gcc()` **故意不缓存**——用户很可能是在软件开着的时候才去装，
装完点「跑一下」就该立刻能用，不该要求重启。查找除了 PATH，还会去 winget 的
安装目录翻一遍（跟 `find_ffmpeg` 一个套路）。

## 2026-10-11 补三个"不算缺口、迟早会疼"的地方

规划里的功能全做完之后，用户问"还有缺口吗"。复盘出三条**不是功能缺失、
但时间一长一定疼**的事：

### 1. 数据库自动备份（最要紧）

`data/cstudy.db` 里装着全部学习数据，而它躺在单个文件里，**之前一份自动备份都没有**
（只有我手动复制的几个 `.bak`）。

关键在于**分清哪些能重建、哪些不能**：
- 1833 道题 —— 能重建，`scripts/import_bank.py` 跑一遍就回来了
- **作答记录和错题本 —— 不能重建**。这是六个月的学习轨迹，丢一次就没法重来

所以启动时顺手备一份（`Database.backup()`），一天一次、留最近 14 份。

**用 SQLite 自己的 `backup()` API，不是复制文件**——直接复制有可能拿到
"写到一半"的库，备份出来是坏的，而备份坏掉最糟的地方是**你不知道它坏了**。

### 2. 学情统计

用户自己定的复盘方式是"每周看错题本净减少、每月看模拟分数"，但这两个**界面上都没地方看**。
`answers` 表一直在记（时间、对错、用时），只是没人读。

- **按周统计不按天**：一天没做题很正常，按天看全是窟窿，看着打击人
- **分题型算正确率**，不是只算总分：总分 70% 可能掩盖着"程序填空只有 30%"，
  而那才是丢分的地方。这跟当初 C 语言把"程序填空"从"填空"里分出来是同一个道理

### 3. 笔记检索

原来笔记页只能显示"刚生成的那一篇"，关掉软件就只能去 `notes/` 翻一堆 `.md`。
2 篇的时候无所谓，50 篇之后"哪一集讲过位运算"就变成天天要问的问题。

`search_notes()` **标题和正文一起搜**——用户记不住是哪一集，只记得住"位运算"这个词。

### 顺手做的重构

时间戳的 UTC→本地转换原来只在 `wrong_book.py` 里有一份，学情统计也要用，
所以抽成了 `db.parse_db_time()`。**这个坑（SQLite 的 CURRENT_TIMESTAMP 是 UTC）
在 `answers.answered_at`、`wrong_questions.last_wrong_at`、`notes.created_at`
上都存在**，集中一份不容易漏。

**踩的坑**：统计面板的每周横条图第一版全挤在一行——渲染成图片才发现。
整段 HTML 是 `"".join(parts)` 拼的，忘了在行之间加 `\n`。
**光跑测试发现不了这种问题，得真渲染出来看。**

  和视频关键帧都很准（VS 编辑器里的代码、PPT 正文都能一字不差读出来）。
